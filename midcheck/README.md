# 에이전트 중간 점검: 목표 타당성 점검 절차 안내서

에이전트를 여러 개 만들고, 합치고, 연결하는 단계에 있는 분을 위한 점검 지침서입니다.
에이전트를 더 만들기 전에 "지금 만든 것이 처음 목표에 맞는가"를 멈추고 확인하는 방법을 정리했습니다.

- 대상: 에이전트를 2~5개 만들어 본 개인, 소규모 팀
- 기준일: 2026-11-24
- 근거: Claude Code 공식 문서, Codex 공식 문서, 실무 연구 1편(원문 확인 완료)

---

## 여는 이야기

처음 에이전트는 잘 굴러갑니다. 자료를 정리하는 에이전트, 글을 다듬는 에이전트, 파일을 옮기는 에이전트가 각자 맡은 일을 합니다.

그런데 네 번째를 붙이는 순간부터 이상한 일이 생깁니다. 두 에이전트가 같은 자료를 정리하고, 어느 쪽 결과가 최종인지 아무도 모릅니다. 결국 합치는 데 며칠이 걸립니다.

이런 일은 코드가 나빠서 생기지 않습니다. **목표를 중간에 다시 확인하지 않아서** 생깁니다. 이 안내서는 그 확인을 정해진 순서로 하도록 돕습니다.

> 예시 시나리오: "자료 정리 에이전트"와 "보고서 요약 에이전트"가 같은 폴더를 읽고 같은 요약을 만들고 있었습니다. 둘 중 하나를 없애기로 하고 되돌아보니, 처음 목표 문장에 "요약은 한 곳에서만 만든다"가 없었던 것이 원인이었습니다.

---

## 1장. 언제 멈추고 점검하는가

다음 네 시점에 점검합니다.

| 시점 | 이유 |
|---|---|
| 에이전트 2개, 3개, 5개째를 만들기 직전 | 새 에이전트가 기존 것과 겹치는지 먼저 확인 |
| 두 에이전트를 합치기 직전 | 어느 쪽 결과를 기준으로 할지 정함 |
| 여러 에이전트를 연결(오케스트레이션)하기 직전 | 누가 무엇을 먼저 하는지 정함 |
| 2주에 한 번 정기 | 처음 목표에서 멀어지지 않았는지 확인 |

**신호로 삼을 것.** 같은 실수나 같은 수정 요청이 두 번 반복되면 멈추십시오. Codex 공식 가이드는 "Codex가 같은 실수를 두 번 하면 회고를 요청하고 AGENTS.md를 고치라"고 권합니다. Claude Code 공식 가이드도 같은 수정이 두 번 실패하면 세 번째 수정을 하기보다 `/clear` 후 더 나은 지시로 다시 시작하라고 합니다.

---

## 2장. 목표 타당성 5문항

에이전트마다 아래 다섯 문항에 답합니다. 답이 비어 있으면 그 에이전트는 아직 만들 준비가 되지 않은 것입니다.

**① 한 문장 목표.** "이 에이전트는 [입력]을 받아 [결과]를 만든다." 형식으로 씁니다.
- 좋은 예: "주간 회의록을 받아 결정 사항 목록을 만든다."
- 나쁜 예: "업무를 도와준다." (무엇을 받아 무엇을 내는지 없음)

**② 끝 조건.** 무엇이 참이면 이 에이전트의 일이 끝난 것인지 씁니다. Codex 공식 가이드는 프롬프트에 "Done when(완료 조건)"을 넣으라고 권합니다. Claude Code에서는 `/goal`로 조건을 걸 수 있습니다.
- 예: "결정 사항이 5개 이하이고, 각 항목에 담당자 이름이 있으면 끝."

**③ 담당 경계.** 이 에이전트가 하지 않을 일을 최소 한 개 씁니다. 이 항목이 없으면 나중에 다른 에이전트와 일이 겹칩니다.
- 예: "회의록을 요약만 하며, 일정 등록은 하지 않는다."

**④ 중복 검사.** 기존 에이전트 목록(부록 B)과 입력, 출력, 실행 시점을 비교합니다. 자세한 절차는 3장에 있습니다.

**⑤ 검증 방법.** 결과가 맞는지 사람이 또는 자동으로 확인하는 방법을 씁니다. Claude Code 공식 가이드는 Claude에게 확인할 수 있는 도구를 주라고 권합니다. 예를 들어 테스트 명령이나 체크 스크립트가 있습니다. 반드시 지켜야 하는 확인은 프롬프트에만 쓰지 말고 훅으로 강제하라고 합니다.

---

## 3장. 중복 탐지 절차

합치는 데 시간이 많이 드는 이유는 대부분 중복을 늦게 발견하기 때문입니다. 아래 순서로 만들기 전에 찾으십시오.

1. **목록 만들기.** 지금 있는 에이전트와 만들 예정인 에이전트를 부록 B 표에 모두 적습니다.
2. **네 가지 열 비교.** 입력, 출력, 실행 시점(언제 돌아가는가), 쓰는 도구를 열로 놓고 봅니다.
3. **후보 표시.** 네 열 중 두 개 이상이 같으면 중복 후보입니다.
4. **판정.** 아래 4장의 기준으로 유지, 통합, 분리, 중단 중 하나를 고릅니다.
5. **통합할 때의 원칙.** 결과를 최종으로 정하는 에이전트는 하나만 둡니다. 나머지는 스킬이나 하위 작업으로 바꿉니다.
   - Codex 공식 가이드는 반복되는 작업을 스킬로 묶으라고 권하고, 스킬은 한 가지 일만 하도록 범위를 좁히라고 합니다.
   - Claude Code 공식 가이드는 하위 에이전트가 토큰 비용을 더 쓴다는 점을 알고 쓰라고 합니다. 작은 일을 하위 에이전트로 나누면 비용이 늘 수 있습니다.

## 4장. 판정 기준

| 판정 | 조건 | 할 일 |
|---|---|---|
| 계속 | 목표 한 문장, 끝 조건, 담당 경계가 모두 있고 중복 후보가 0~1개 | 그대로 진행 |
| 축소 | 경계 밖 일이 2개 이상 섞여 있음 | 일을 나눠 한 가지씩만 남김 |
| 통합 | 입력과 출력이 둘 다 겹침 | 결과를 정하는 쪽 하나로 합치고 나머지는 스킬로 바꿈 |
| 중단 | 끝 조건을 쓸 수 없음, 또는 사람 승인 없이 외부에 영향을 줌 | 만들기를 멈추고 목표부터 다시 씀 |

## 5장. 점검표

에이전트 하나당 아래 항목을 확인합니다.

- [ ] 한 문장 목표를 썼다.
- [ ] 끝 조건을 썼고, 확인할 수 있는 말로 썼다.
- [ ] 하지 않을 일을 한 개 이상 썼다.
- [ ] 기존 에이전트와 입력, 출력, 실행 시점을 비교했다.
- [ ] 결과를 확인하는 방법이 있다(테스트, 체크 명령, 사람 확인 중 하나 이상).
- [ ] 반드시 지켜야 하는 규칙은 프롬프트가 아니라 설정이나 훅에 두었다.
- [ ] 외부에 글을 올리거나 파일을 지우는 동작은 사람이 승인하도록 되어 있다.
- [ ] 이번 점검에서 판정(계속, 축소, 통합, 중단)을 한 가지로 기록했다.

## 6장. 공식 문서 근거

### Claude Code (code.claude.com/docs/en/best-practices)

- **지시는 두 종류로 나누어 쓰라.** 프롬프트, CLAUDE.md, 스킬은 모델이 읽고 판단하는 지시입니다. 훅, 권한 규칙, 관리 설정은 도구가 매번 실행하는 지시입니다. 반드시 매번 지켜져야 하는 일은 훅, 권한 규칙, 관리 설정 중 하나로 만들라고 합니다.
- **Claude에게 확인할 방법을 주라.** 완료 기준을 확인할 명령이 있어야 Claude가 스스로 점검할 수 있습니다.
- **두 번 실패하면 다시 시작하라.** 같은 수정이 두 번 실패하면 `/clear` 후 더 나은 지시로 시작합니다.
- **하위 에이전트는 비용이 든다.** 하위 에이전트는 자기 요청을 따로 보내고, 그 비용은 본 세션과 같은 사용량에 더해집니다.
- **사용량은 `/usage`로 본다.** 스킬, 하위 에이전트, 플러그인, MCP 서버별로 사용량을 나눠 볼 수 있습니다.

### Codex (learn.chatgpt.com/guides/best-practices)

- **어려운 일은 계획부터.** 복잡하거나 애매한 작업은 코딩 전에 계획 모드(`/plan`)로 먼저 정리하라고 권합니다.
- **완료 조건을 프롬프트에 넣어라.** 목표, 맥락, 제약, 완료 조건의 네 가지를 넣으라고 합니다.
- **AGENTS.md는 짧고 정확하게.** 같은 실수가 반복될 때만 규칙을 추가합니다.
- **한 대화는 한 가지 결과 단위로.** 프로젝트 전체를 한 대화에 담으면 맥락이 부풀어 결과가 나빠진다고 합니다.
- **흔한 실수 목록.** 지속되는 규칙을 프롬프트에 몰아넣기, 계획 건너뛰기, 수동으로 안정되기 전에 예약 작업부터 걸기, 프로젝트 전체를 한 대화에 담기가 포함되어 있습니다.

## 7장. 실무 연구에서 얻는 점검 포인트

Anthropic 연구 "How Claude Code is used in practice"(2026-06-16)는 2025년 10월부터 2026년 4월까지 약 40만 건의 Claude Code 세션을 분석했습니다. 주요 결과는 다음과 같습니다.

- **계획은 사람, 실행은 에이전트.** 일반적인 세션에서 무엇을 할지에 대한 결정의 약 70%는 사람이 내렸습니다. 어떻게 할지에 대한 결정의 약 80%는 Claude가 내렸습니다.
- **목표를 잘 아는 사람일수록 한 지시로 더 많이 해낸다.** 초보 수준으로 평가된 세션은 프롬프트 하나당 평균 약 5번의 작업을 이어갔고, 전문가 수준 세션은 약 12번이었습니다.
- **막혔을 때 포기하는 비율.** 초보 수준 사용자가 문제가 생긴 세션을 포기한 비율은 19%였고, 나머지는 5~7%였습니다.

**이 연구가 점검에 주는 의미.** 목표 설정과 끝 조건은 에이전트에게 맡길 수 없는 사람의 몫입니다. 목표가 흐릿한 상태에서 에이전트를 더 만들면, 막힐 때 되돌릴 기준이 없습니다. 2장의 다섯 문항이 바로 그 기준입니다.

> 이 연구는 대화형 Claude Code 사용 데이터를 분석한 것입니다. 개인 프로젝트에 그대로 옮기기 전에 자신의 세션으로 한 번 확인하십시오.

```

작성일:

1. 한 문장 목표: 이 에이전트는 [        ]을 받아 [        ]를 만든다.
2. 끝 조건(Done when): 
3. 하지 않을 일:
4. 입력 / 출력 / 실행 시점:
5. 확인 방법(테스트, 체크 명령, 사람 확인):
6. 판정(계속 / 축소 / 통합 / 중단) 과 이유:
```
